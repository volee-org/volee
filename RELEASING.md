# Releasing volee

This guide is for maintainers. It describes how a version of volee goes from
`main` to a GitHub release with prebuilt binaries, and how to add crates.io and
Homebrew later.

## How a release works

- **One distributed package.** Only `volee-cli`, which builds the `volee`
  binary, is distributed. `dist-workspace.toml` sets `dist = false` for the
  whole workspace and `crates/volee-cli/Cargo.toml` opts back in, so the
  library crates (and any crate added later) are never packaged by accident.
- **One version.** Every crate inherits `version` from `[workspace.package]` in
  the root `Cargo.toml`, and the tag is that version with a `v` prefix.
- **A reviewed release pull request, then a tag.** A maintainer opens a pull
  request that sets the version and regenerates `CHANGELOG.md`, merges it once
  CI passes, and pushes a `vX.Y.Z` tag on the merged commit. GitHub Actions
  cannot open pull requests in this organization, so no bot prepares releases.
- **The tag builds the release.** The `Release` workflow
  (`.github/workflows/release.yml`, generated by
  [dist](https://opensource.axo.dev/cargo-dist/)) checks that the tag matches
  the version of `volee-cli`, builds `volee` natively on four runners, builds
  the installer and the checksums, then creates the GitHub release. Its notes
  are the version's section of `CHANGELOG.md` followed by install instructions.
- **Pull requests only plan.** On pull requests the same workflow runs its
  `plan` job only (`pr-run-mode = "plan"`): it checks the configuration and
  builds nothing.

Each release contains these files:

| File | Content |
| --- | --- |
| `volee-cli-aarch64-apple-darwin.tar.xz` | macOS on Apple Silicon (built on `macos-15`) |
| `volee-cli-x86_64-apple-darwin.tar.xz` | macOS on Intel (built on `macos-15-intel`) |
| `volee-cli-aarch64-unknown-linux-gnu.tar.xz` | Linux on ARM64, glibc 2.35 or later (built on `ubuntu-22.04-arm`) |
| `volee-cli-x86_64-unknown-linux-gnu.tar.xz` | Linux on x86_64, glibc 2.35 or later (built on `ubuntu-22.04`) |
| `volee-cli-installer.sh` | Shell installer: picks the archive for the machine, checks its SHA-256 checksum and installs `volee` |
| `*.sha256`, `sha256.sum` | SHA-256 checksums, one file per artifact and one for all of them |
| `source.tar.gz` | The source tree at the tag |
| `dist-manifest.json` | Machine-readable description of the release |

Each archive holds `volee`, `README.md`, `CHANGELOG.md`, `LICENSE-MIT` and
`LICENSE-APACHE`. The installer puts `volee` in `$XDG_BIN_HOME`, else
`$XDG_DATA_HOME/../bin`, else `~/.local/bin`, and adds that directory to
`PATH` in the shell profile when it is missing.

## Tools

| Tool | Install | Used for |
| --- | --- | --- |
| [git-cliff](https://git-cliff.org) | `brew install git-cliff` or `cargo install git-cliff --locked` | Generating `CHANGELOG.md` |
| [cargo-edit](https://github.com/killercup/cargo-edit) | `brew install cargo-edit` or `cargo install cargo-edit --locked` | `cargo set-version` |
| [dist](https://opensource.axo.dev/cargo-dist/) | `brew install cargo-dist` | Checking the release plan locally (optional) |
| [GitHub CLI](https://cli.github.com) | `brew install gh` | Opening the pull request, watching the workflow |

CI installs the dist version pinned in `dist-workspace.toml`
(`cargo-dist-version`), whatever version you have locally. Use the same
version locally: another one may generate a different workflow and make
`dist plan` report `release.yml` as out of date.

## Release procedure

The commands below release `0.2.0`: replace it with your version.

> [!NOTE]
> **v0.1.0**, the first release, needs no version change: the workspace is
> already at `0.1.0`. Skip `cargo set-version` in step 2.

### 1. Choose the version

volee follows [Semantic Versioning](https://semver.org). While it is 0.x, a
release with a new feature or a breaking change bumps the minor version
(0.1.0 to 0.2.0) and a release with only fixes bumps the patch version (0.2.0
to 0.2.1). git-cliff applies these rules to the commit types since the last
tag:

```sh
git switch main
git pull --ff-only
git cliff --bumped-version      # prints for example v0.2.0
```

### 2. Prepare the release branch

```sh
git switch -c release/v0.2.0
cargo set-version --workspace 0.2.0
git cliff --tag v0.2.0 -o CHANGELOG.md
dist plan                       # optional: must announce v0.2.0
```

`cargo set-version` changes the workspace version, the version of every
internal crate in `[workspace.dependencies]` and `Cargo.lock`.
`git diff --stat` must list `Cargo.toml`, `Cargo.lock` and `CHANGELOG.md`, and
nothing else.

Read the new section of `CHANGELOG.md`. Each entry is the title of a pull
request merged since the last release (pull requests are squash-merged, so the
title is the commit message), sorted into
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) sections:

| Commit type | Section |
| --- | --- |
| `feat` | Added, or Deprecated / Removed when the description starts with "deprecate" / "remove", "drop" or "delete" |
| `fix` | Fixed, or Security when the description mentions security, a vulnerability, a CVE or a GHSA |
| `perf`, `revert` | Changed |
| `docs` | Documentation |
| `build`, `chore`, `ci`, `refactor`, `style`, `test` | Left out, unless the change is breaking |

Breaking changes (`feat!:`, or a `BREAKING CHANGE:` footer) are marked
**Breaking:**. Release pull requests and dependency updates are left out.

Do not edit `CHANGELOG.md` by hand: every release regenerates the whole file
from the history, which would silently undo the edit. Fix an entry in
`cliff.toml` instead, then regenerate:

- to reword a title, add a rule at the top of `commit_preprocessors`, for
  example
  `{ pattern = '^feat\(core\): add the event-sourced domain model', replace = 'feat(core): add the domain model, rebuilt from events' }`;
- to drop a commit, add `{ sha = "<full commit hash>", skip = true }` at the
  top of `commit_parsers`.

### 3. Open the release pull request

```sh
git commit -am "chore: release v0.2.0"
git push -u origin release/v0.2.0
gh pr create --repo volee-org/volee --base main \
  --title "chore: release v0.2.0" --body "Release v0.2.0: version bump and changelog."
```

The pull request runs CI and the `plan` job of the Release workflow. Review
the diff (versions and changelog only) and squash-merge it once "CI OK" is
green.

Merge nothing else between generating the changelog and tagging: a pull
request merged in between would ship in the release without appearing in its
notes. If one lands, rebase the release branch on `main` and rerun
`git cliff --tag v0.2.0 -o CHANGELOG.md` before merging.

### 4. Tag the merged commit

```sh
git switch main
git pull --ff-only
git log -1 --oneline            # must be: chore: release v0.2.0 (#NN)
git tag -s v0.2.0 -m "volee v0.2.0"
git push origin v0.2.0
```

`git tag -s` signs the tag with your GPG or SSH signing key; GitHub shows it
as verified when that key is added to your account as a signing key. Without
a signing key, create an annotated tag instead: `git tag -a v0.2.0 -m "volee
v0.2.0"`.

Tag the squash commit on `main`, never the release branch, and use exactly
`v` followed by the version in `Cargo.toml`: the `plan` job refuses a tag that
does not match the version of `volee-cli`.

### 5. Watch the Release workflow

```sh
gh run list --repo volee-org/volee --workflow release.yml --limit 1
gh run watch --repo volee-org/volee <run-id>
```

The jobs run in this order: `plan`, `build-local-artifacts` (one job per
target), `build-global-artifacts` (installer and checksums), `host` (creates
the GitHub release and uploads the files) and `announce`.

### 6. Verify the release

```sh
gh release view v0.2.0 --repo volee-org/volee
```

Check the title (`0.2.0 - <date>`), the notes (the changelog section, then the
install instructions) and the files listed above. Then install it as a user
would. On macOS:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/volee-org/volee/releases/download/v0.2.0/volee-cli-installer.sh | sh
volee --version                 # volee 0.2.0
```

On Linux, in a throwaway container (add `--platform linux/amd64` or
`--platform linux/arm64` to try the other architecture):

```sh
docker run --rm ubuntu:24.04 sh -c '
  apt-get update -qq && apt-get install -y -qq ca-certificates curl xz-utils >/dev/null &&
  curl --proto "=https" --tlsv1.2 -LsSf https://github.com/volee-org/volee/releases/download/v0.2.0/volee-cli-installer.sh | sh &&
  ~/.local/bin/volee --version'
```

Finally, check that the [installation guide](docs/src/guide/installation.md)
and the README still describe what was released.

## When something goes wrong

- **The workflow fails before `host`.** Nothing was published. For a
  transient failure (runner, network), rerun the failed jobs:
  `gh run rerun <run-id> --failed`. If the code or the configuration must
  change, fix it on `main` with a pull request, delete the tag
  (`git push origin :refs/tags/v0.2.0` and `git tag -d v0.2.0`) and tag the
  new commit (step 4). Moving a tag is acceptable only while no release uses
  it.
- **The release is published but broken.** Do not move or delete the tag:
  people may have installed it, and the installer of that release downloads
  from it. Fix the problem on `main` and release a patch version.
- **`plan` fails with "out of date contents".** Someone edited
  `.github/workflows/release.yml` by hand: run `dist generate` and commit the
  result.

## Pre-releases

A version with a pre-release suffix, such as `0.2.0-rc.1`, follows the same
procedure (`cargo set-version --workspace 0.2.0-rc.1`,
`git cliff --tag v0.2.0-rc.1 -o CHANGELOG.md`, tag `v0.2.0-rc.1`), and dist
marks its GitHub release as a pre-release. The `releases/latest` download URL
used in the documentation skips pre-releases. git-cliff only gives stable
versions a section of their own (`tag_pattern` in `cliff.toml`), so the
pre-release section is folded into the stable version when it is released.

## Changing the release configuration

- **`dist-workspace.toml`** configures dist (targets, installers, CI). After
  a change, run `dist generate`, which rewrites
  `.github/workflows/release.yml`, then `dist plan`, and commit both files.
- **Never edit `.github/workflows/release.yml` by hand.** dist checks it
  against its own output on every pull request and before every release, and
  fails when they differ. Dependabot leaves it alone (`exclude-paths` in
  `.github/dependabot.yml`); dist updates its actions instead.
- **To update dist**, install the new version (`brew upgrade cargo-dist`), set
  `cargo-dist-version` in `dist-workspace.toml` to it, run `dist generate` and
  `dist plan`, and open a `ci: update dist to X.Y.Z` pull request.
- **`cliff.toml`** holds the changelog template and the mapping from commit
  types to sections. Preview a change with `git cliff --unreleased`, which
  prints to the terminal.

## Repository settings

- The Release workflow asks for `contents: write` itself, so the default
  workflow permissions stay read-only, and "Allow GitHub Actions to create and
  approve pull requests" stays off.
- Recommended: a tag ruleset (Settings, Rules, Rulesets, New tag ruleset) on
  `refs/tags/v*` that restricts creations, updates and deletions, with the
  maintainers as the only bypass actors. Only maintainers can then start a
  release, and nobody can move a released tag.

## Later: publishing to crates.io

`cargo install volee-cli` needs every workspace crate that `volee-cli` depends
on (`volee-core`, `volee-daemon` and the others) to be on crates.io too.
`cargo publish --workspace` publishes all of them in dependency order.

1. **Publish once by hand.** Trusted Publishing is configured per crate, so
   each crate must exist first. Create a crates.io API token with the
   `publish-new` and `publish-update` scopes, restricted to the `volee*`
   crates, then from the tagged commit run
   `cargo publish --workspace --locked --dry-run` and
   `cargo publish --workspace --locked`. Revoke the token afterwards.
2. **Set up Trusted Publishing** (no long-lived secret). On crates.io, in the
   settings of each crate, add a GitHub trusted publisher: owner `volee-org`,
   repository `volee`, workflow `release.yml`. crates.io checks the top-level
   workflow, and the publish job below is called by `release.yml`.
3. **Add a publish job.** Create `.github/workflows/publish-crates.yml`:

   ```yaml
   name: Publish crates
   on:
     workflow_call:
       inputs:
         plan:
           required: true
           type: string
   jobs:
     publish:
       runs-on: ubuntu-latest
       permissions:
         contents: read
         id-token: write
       steps:
         - uses: actions/checkout@<sha> # pin like the CI workflow does
           with:
             persist-credentials: false
         - uses: dtolnay/rust-toolchain@<sha>
           with:
             toolchain: "1.99"
         - uses: rust-lang/crates-io-auth-action@<sha> # v1
           id: auth
         - run: cargo publish --workspace --locked
           env:
             CARGO_REGISTRY_TOKEN: ${{ steps.auth.outputs.token }}
   ```

   Then declare the job in `dist-workspace.toml` (`publish-jobs` goes in the
   `[dist]` table, the permissions table at the end of the file) and run
   `dist generate`:

   ```toml
   publish-jobs = ["./publish-crates"]

   [dist.github-custom-job-permissions]
   "publish-crates" = { contents = "read", id-token = "write" }
   ```

   A called workflow never gets more permissions than its caller grants, and
   dist grants publish jobs `id-token` and `packages` only, hence the table.
   dist calls the job after the GitHub release is created, passes it the
   repository secrets, and skips it for pre-releases
   (`publish-prereleases = false`).
4. **Or use a token** instead of Trusted Publishing: store it as the
   `CARGO_REGISTRY_TOKEN` repository secret, preferably in an environment
   with required reviewers, and drop the `crates-io-auth-action` step.
5. **Document it**: add `cargo install volee-cli --locked` to the
   installation guide and the README.

## Later: a Homebrew tap

The release does not include a Homebrew formula yet. Homebrew only installs
formulae from a tap ("Homebrew requires formulae to be in a tap"), and without
a tap dist's release notes would advertise `brew install volee`, which
homebrew-core does not have.

1. **Create the tap**: a public repository named `volee-org/homebrew-tap`
   (the `homebrew-` prefix is required), with a README. Users then run
   `brew install volee-org/tap/volee`.
2. **Create a token that can push to it**: a fine-grained personal access
   token (or a GitHub App token) with "Contents: read and write" on
   `volee-org/homebrew-tap` only. The organization may have to approve it.
   Store it in `volee-org/volee` as the repository secret
   `HOMEBREW_TAP_TOKEN`.
3. **Configure dist**: in `dist-workspace.toml`, under `[dist]`,

   ```toml
   installers = ["shell", "homebrew"]
   tap = "volee-org/homebrew-tap"
   publish-jobs = ["homebrew"]
   ```

   (with crates.io publishing set up too, list both jobs:
   `publish-jobs = ["homebrew", "./publish-crates"]`), and in
   `crates/volee-cli/Cargo.toml`, name the formula after the binary
   rather than the package:

   ```toml
   [package.metadata.dist]
   dist = true
   formula = "volee"
   ```

   Then run `dist generate`. The new `publish-homebrew-formula` job runs
   after the GitHub release is created, commits `Formula/volee.rb` to the tap
   and pushes it directly (no pull request), and skips pre-releases.
4. **Document it**: add `brew install volee-org/tap/volee` to the
   installation guide and the README.
