# AGENTS.md

Instructions for coding agents (Claude Code, Codex, Cursor and others)
working on this repository. Humans: [CONTRIBUTING.md](CONTRIBUTING.md) says
the same things at a gentler pace.

## What volee is

A control tower for Claude Code agents, written in Rust with a web interface.
It observes Claude Code (hooks over `http`, `claude agents --json`,
transcripts, git), puts what needs a decision in an inbox in the browser
(permissions, questions, finished work read in layers), and does the actions
(merge, fix request, editor). Rules and configuration are Lua. It never starts
an agent, holds a terminal or types into one. This is v2, on the `v2` branch;
`main` still holds the old 0.x tool until v2 is merged.
Read [docs/src/architecture/overview.md](docs/src/architecture/overview.md)
before changing anything structural, `docs/v2/framing.md` for why, and the
decisions in [docs/src/adr/](docs/src/adr/README.md) (0036 to 0041 are v2)
before contradicting one.

## Repository map

| Path | What lives there |
| --- | --- |
| `crates/volee-daemon` | The daemon: hook server, agents view, held decisions, rules host, review, actions (`actions/`), the web API (`web/`), the work screen (`work/`) |
| `crates/volee-rules` | The sandboxed Lua engine (mlua), typed `Change` and `FinishedFacts`. Depends on no other volee crate. |
| `crates/volee-config` | `config.lua` |
| `crates/volee-store` | SQLite: hook events, journal, comments, reviews, caches |
| `crates/volee-git` | git and the forge through your own `git` and `gh` |
| `crates/volee-harness` | The Claude Code profile and the hook settings |
| `crates/volee-core`, `volee-proto`, `volee-mcp` | The 0.x domain model, socket protocol and MCP server, being reduced (`ask_human` stays) |
| `crates/volee-cli` | The `volee` binary: argument parsing and wiring only |
| `ui/` | The web interface: Svelte 5, TypeScript, Vite, npm. Built into `ui/dist`, which the daemon embeds. |
| `docs/` | The mdBook site (`docs/src`), ADRs (`docs/src/adr`), theme (`docs/theme`, vendored), v2 notes and trials (`docs/v2`) |
| `journeys/` | What a person does, done for real, with a real Claude Code. The release gate; never run in CI. Being rebuilt as browser journeys. |
| `.github/` | CI, the release workflow (generated by dist), issue forms, Dependabot. |
| `RELEASING.md`, `dist-workspace.toml`, `cliff.toml` | Release procedure, release artifacts (dist), changelog generation (git-cliff). |

Dependencies point inward: `volee-core` and `volee-rules` depend on no other
volee crate.

## Commands

Run these before you say a change is done. They are exactly what CI runs.

```sh
cargo fmt --all
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo nextest run --workspace --all-features --locked   # or: cargo test --workspace
cargo test --doc --workspace --locked
typos
mdbook build docs                                        # when docs/ changed (needs mdbook-mermaid)
(cd ui && npm ci && npm run check)                       # when ui/ changed: lint, typecheck, tests, build
cargo test -p volee-daemon --test web --locked           # with ui/dist built: the daemon serving the real bundle
```

`just check` runs the first three. The toolchain is pinned by
`rust-toolchain.toml`; the MSRV (`rust-version` in `Cargo.toml`) is checked in
CI, so do not use language or library features newer than it. `cargo build`
needs no Node: `crates/volee-daemon/build.rs` embeds `ui/dist` when it exists
and a stub page otherwise. A release build sets `VOLEE_REQUIRE_UI=1`.

## Code rules

- English everywhere: code, comments, docs, interface text, commit messages.
- Errors: `thiserror` in library crates, `anyhow` only in `volee-cli`. No
  `unwrap()` or `expect()` outside tests unless the invariant is written next
  to it.
- No `println!`/`eprintln!` outside `volee-cli`. Use `tracing` for diagnostics.
- No `unsafe` (the workspace forbids it).
- Keep functions pure where you can and push IO to the edges; the domain is
  tested without IO.
- Never parse Claude Code internal files (`~/.claude/jobs`, `~/.claude/sessions`).
  Use hooks, `claude agents --json` and documented commands (ADR 0004).
  Transcripts are the one exception, read only by
  `crates/volee-daemon/src/transcript.rs`, which skips what it does not
  understand and degrades to hooks and git (ADR 0040).
- Observe, never own: no code starts an agent, holds a terminal or types into
  one. A decision goes back to Claude Code through a hook response; the only
  message volee sends is a fix request the person asked for (ADR 0041).
- Never edit the user's own configuration files (for example
  `~/.claude/settings.json` or `~/.claude.json`) on your own. `volee doctor`
  writes the hook entries into the one file the person names, and only when run;
  tests and trials pass hooks with `--settings` or use an isolated config
  directory.
- Lua (`volee-rules`) only decides: Rust owns the facts and the effects. Keep
  the sandbox limits in Rust, and keep the safest answer as the fallback (ADR
  0037).
- Destructive operations need delivery evidence and never delete branches
  (ADR 0011).

## Tests

- Unit tests sit next to the code (`#[cfg(test)] mod tests`).
- The web interface keeps its logic in plain `.ts` modules tested with Vitest
  without a DOM (`ui/tests`); components stay thin. The daemon's web API is
  tested in `crates/volee-daemon/tests/web.rs` against the real bundle.
- Git code is tested against real temporary repositories (`tempfile`).
- Tests never touch the network, the user's home directory or a real Claude
  Code installation. Use fakes behind the crate's traits.
- The [journeys](journeys/README.md) are the exception, and they are not
  tests: scripts that do what a person does, with a real Claude Code. They
  never run in CI, and no version is released unless they pass
  ([RELEASING.md](RELEASING.md)). When you change what a person does in the
  interface, run a real trial in a sandbox repository before you say the change
  is done, and write it down (see `docs/v2/*.md`).

## Commits and pull requests

- Conventional Commits, English, imperative: `feat(daemon): hold a question for a short delay`.
  Scopes are crate names without the `volee-` prefix, or `ui`, `docs`, `ci`, `deps`.
- Pull requests are squash-merged; the PR title becomes the commit message, so
  it must follow the same format. It also becomes the changelog entry: write
  it for users.
- One topic per pull request. Update docs and ADRs in the same pull request as
  the code they describe.
- Do not edit `CHANGELOG.md` or version numbers: maintainers change them in
  release pull requests ([RELEASING.md](RELEASING.md)).
- Never edit `.github/workflows/release.yml` by hand: change
  `dist-workspace.toml` and run `dist generate`.

## When you are unsure

Prefer the smallest change that keeps the design coherent, explain the
trade-off in the pull request, and propose an ADR for anything that changes a
recorded decision.
